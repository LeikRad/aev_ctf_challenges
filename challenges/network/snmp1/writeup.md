## Recon
UDP 8024 (non-standard, not 161) speaks SNMP v1/v2c, community `public`. The textbook
command - `snmpwalk -v2c -c public snmp1.chal.deti:8024 1.3.6.1` - **aborts**:
```
snmpwalk: Protocol error (Expected RESPONSE-PDU but got SET-PDU)
```
The agent replies with a **SET-PDU (tag 0xa3)** instead of a GET-RESPONSE (0xa2), so
Net-SNMP refuses it. Worked around by (a) reading replies off the wire with
`tcpdump -A udp port 8024`, and (b) a scapy walker that parses the reply regardless of
the wrong PDU tag (`snmp-walker.py`). Full walk in
`../../../10.110.3.72/snmp-walk.txt`.

## Private enterprise tree (the leak)
Walking past MIB-II, the agent answers under the **private enterprise** branch
`1.3.6.1.4.1`:
```
1.3.6.1.4.1.99999.1.1.0 = flag{3cad557d9709a6a658ae582ce33ab216}
```
`.4.1` is `enterprises`; `99999` is a bogus/made-up enterprise number. The flag lives
here, outside the standard groups - which is why reading only sysDescr/sysContact/
sysLocation misses it and you must **walk** the whole tree.

## Flag
```
flag{3cad557d9709a6a658ae582ce33ab216}
```

## Which node is generated on demand - and what it implies (task question)
- The **MIB-II nodes are static** (inventory read from the kernel/config).
- The **private `.99999` node is generated on demand**: its value is produced by the
  agent when queried, not stored in a MIB file. In Net-SNMP that means the OID is
  backed by a **`pass` / `exec` / `extend`** directive in `snmpd.conf` - i.e. the agent
  **runs a program/script and returns its stdout** as the OID value. The sysObjectID
  `...8072.*` (net-snmp) and the non-conformant hand-rolled responses are consistent
  with a scripted/custom agent.
- **Implication:** if the agent shells out to answer a query, SNMP is a
  **command-execution surface**. Net-SNMP's `extend`/`exec` run shell commands; and if
  a **writable** community exists, the `NET-SNMP-EXTEND-MIB` lets a client *define new*
  commands to run via SNMP SET - turning the agent into remote code execution. Even
  read-only, "a value generated by running a program" means the attack surface is
  whatever that program does with its inputs.
- **In scope here:** we only *read* the tree (RoE: no exploitation). The exec capability
  is reported as a finding, not exercised.

## Root cause & remediation
- **Cause:** world-readable `public` community exposes a private OID carrying a secret;
  the agent also serves on an odd port with non-conformant PDUs and an on-demand
  (script-backed) node.
- **Fix:** rotate the community string off `public`, restrict SNMP to management hosts,
  prefer SNMPv3 with auth+priv, never place secrets in MIB values, and remove/sandbox
  any `exec`/`extend`/`pass` directives (and ensure no writable community can reach the
  EXTEND MIB). Report the SET-PDU behaviour as an agent defect.
